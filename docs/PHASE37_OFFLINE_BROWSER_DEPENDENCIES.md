# Phase 37 — Dependency supply-chain readiness and offline build handoff

Baseline: exact YadiLab Foundation v0.36.0 ZIP; Masterprompt v1.2 remains the architectural authority. This phase does not change Engine or scenario semantics.

## Problem closed

The previous readiness test accepted a root-only `package-lock.json` combined with hand-written direct `node_modules/*/package.json`. That is **not** a reproducible or integrity-checked dependency installation. The test fixture's old `ready=true` did not establish any installed transitive packages.

## New fail-closed gates

1. Exact source `package.json` runtime and development pins must match the existing dependency policy.
2. A version-3 npm lock must include a concrete record for **every direct dependency**, with matching exact version, SHA-512 SRI and canonical npm-registry HTTPS resolved path.
3. Every lock entry must have a safe npm install path, exact version, SHA-512 SRI, and allowed registry origin. Reachability follows non-optional transitive dependencies, including nested installs.
4. `node_modules/.package-lock.json`, generated by npm, must agree with the project lock for **every installed package** (version, integrity, origin). Every required transitive package must appear in the installed lock. Additional undeclared installed entries fail.
5. Each installed lock entry must have a physical `package.json` whose package name and version agree with the project lock.
6. Only when these checks pass can the browser build proceed to esbuild bundling and actual bundle-resolved third-party inventory/asset hashing.

This is **metadata/lock consistency**, not publisher authenticity or independent verification of every installed file's cryptographic contents. Actual `npm ci` validates tarball SRI during installation, and the browser build still must succeed independently.

## Running the build on an internet-connected development machine

Use the **same v0.37.0 source checkout** and a trusted **Linux x86-64** development machine with Node/npm:

```bash
bash scripts/prepare_offline_browser_cache.sh /path/to/empty/yadilab-npm-cache
```

This developer-only script obtains a complete npm-generated lock if necessary, uses `npm ci`, validates readiness, then saves an npm cache and checksum-protected lock. Do not commit the cache or node_modules to source-control releases.

Transfer the output directory to the air-gapped Linux x86-64 builder, together with the same YadiLab source checkout. On the offline builder:

```bash
bash scripts/install_offline_browser_dependencies.sh /path/to/yadilab-npm-cache
```

The second script uses mandatory `npm ci --offline`, then runs dependency-readiness, real esbuild browser bundling, and the loopback distribution build. It never needs live npm-registry access; missing cache entries fail rather than fetching from the network. Archive transport/storage security is outside the scripts: transfer only a trusted developer-generated cache. Review npm lifecycle scripts and transitive licenses before releasing.

**End users** receive the prebuilt browser bundle and launcher, never a Node/npm requirement. Real Chromium/Firefox/Parrot acceptance remains mandatory before claiming production readiness.
