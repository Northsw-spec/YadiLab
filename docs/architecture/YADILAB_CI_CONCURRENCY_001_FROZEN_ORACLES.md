## Problem and scope
Previous import PR #92 created hundreds of GitHub-hosted Action runs after sequential commits to the same PR; obsolete commits occupied runners and delayed new checks. Add workflow-level cancel-in-progress for **superseded PR runs of the same workflow and PR only**. No runtime/app source or test logic changes. Do not weaken required CI, independent regressions, actual Chromium with pinned OS dependencies, or protected main/release provenance.

## Frozen implementation specification
- Protect **all current workflows triggered by `pull_request`**, including path-filtered independent Chromium/security workflows, required CI, and named manifests. A push-only independent `.github/workflows/release-identity.yml` remains exempt from PR supersession and must not be accidentally changed in behavior.
- Use top-level `concurrency`, with a group containing a **workflow identity and PR identity**. `github.workflow_ref` is a workflow-file identity including workflow ref, `github.event.pull_request.number` identifies the current PR, and `github.run_id` provides a **unique fallback** for non-PR or dispatch runs. Use `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. Ensure PR events on different PR numbers never cancel each other, and separate workflow files never share a cancellation group. Non-PR runs have unique groups and cancellation disabled, so they are never cancelled by these PR changes.
- Keep existing `on`/path filters, triggers, jobs, steps, permissions, runner choices, pinned dependencies, test commands, secrets policy and artifact retention untouched. No job-level cancellation that could skip mandatory checks and no global `main` cancellation.
